# ADR 0001: Migrate piedresyarena.com from WordPress to a static site

- **Status:** Accepted
- **Date:** 2026-10-17

## Context

piedresyarena.com is a personal blog about bicycle trips around the world. It runs on WordPress with the Explorable theme (Elegant Themes), whose home page is a map of the trip stages, and ten plugins:

- akismet
- a Google Maps API key plugin
- asesor-cookies
- better-search-replace
- captcha
- easing-slider
- really-simple-ssl
- w3-total-cache
- wordpress-seo
- wp-encrypt

Only one person edits the site. Readers never interact with it. Even so, WordPress brings a database, PHP hosting, an admin panel, plugin updates, spam and security issues. None of it is needed, and it only causes problems.

The goal is a static site that lives in this repository and is maintained by editing files and pushing. There is no backend, admin panel, comments, contact form or cookie banner.

### Available sources

- `old/piedresy_piedresyarena.sql`: a MariaDB 10.6 dump exported with phpMyAdmin, with table prefix `pya_`.
- `old/uploads/`: a backup of `wp-content/uploads` with 5,962 files. Of these, 479 are originals and the rest are `-WxH` thumbnails generated by WordPress. The 318 images used by the migrated content are all present: 64 featured images (one per stage), 235 images inside the post bodies, 8 in a `[tabs]` block and 12 in the about page slider (one image is both a featured image and a body image).
- `img/logo.png`: the site logo, now in `src/assets/logo.png`.

### What the content looks like

- **Stages:** each trip stage is a custom post type `listing`, served at `/listing/<slug>/`. Each stage has these metadata fields:
  - latitude and longitude: `_et_listing_lat`, `_et_listing_lng`
  - address: `_et_listing_custom_address`
  - short description: `_et_listing_description`
  - rating: `_et_author_rating`
  - featured image: `_thumbnail_id`
  - Yoast SEO title and description
- **Old slugs:** two stages were renamed after publishing. WordPress keeps their previous slugs in `_wp_old_slug` and redirects them.
- **Grouping:** stages are grouped by two taxonomies:
  - `listing_type`, the trip, served at `/listing_type/<slug>/`;
  - `listing_location`, the country or region, served at `/listing_location/<slug>/`.

  Neither taxonomy has term descriptions.
- **Shortcodes and embeds** in the post content:
  - `[caption]` (99 uses);
  - `[button]` (94 uses, almost all of them "Siguiente etapa" links);
  - one `[tabs]/[imagetab]` block of 8 images, in Etiopía Wild Bike stage 6;
  - one `[easingslider id="700"]` on the "A los pedales" page, a slider of 12 images;
  - 3 YouTube iframes and 4 bare YouTube URLs (oEmbed), all in stages.
- **Images** are served from `/wp-content/uploads/YYYY/MM/`.
- **Language:** the site is in Spanish (`es_ES`).

## Decision

### Scope

**Migrated:**

- The 64 published stages, grouped into 12 trips:

  | Trip | Slug | Country | Stages |
  |---|---|---|---|
  | Raid Al Magrib | `raid-al-magrib-2003` | Marruecos | 1 |
  | Mongolia Bike Challenge | `mongolia-bike-challenge-2010` | Mongolia | 9 |
  | Jordania, de Madaba a Áqaba | `jordania-2011` | Jordania | 6 |
  | Etiopía Wild Bike | `etiopia-wild-bike-2012` | Etiopía | 9 |
  | Camino de Santiago con Planeta Bike | `camino-de-santiago-2013` | España | 1 |
  | Namibia | `namibia-2015` | Namibia | 8 |
  | Camino Primitivo | `camino-primitivo-2016` | España | 4 |
  | Ruta de la Plata | `ruta-de-la-plata-2016` | España | 4 |
  | Tanzania | `tanzania-2017` | Tanzania | 5 |
  | Eslovenia | `eslovenia-2018` | Eslovenia | 6 |
  | Georgia | `georgia-2019` | Georgia | 6 |
  | Ardennes Arbalète | `ardennes-arbalete-2022` | Bélgica | 5 |

  In WordPress, the two Camino de Santiago trips (2013 and 2016) share the `listing_type` term `camino-de-santiago`. They are split into two trips here, because they are different journeys years apart.

  The trips are defined in `src/content/trips.yaml`, with their name, year, country and map colour. The country belongs to the trip, not to each stage, and is only display text.

- The "A los pedales" page, the "about me" page. It moves to `/sobre-mi/`.

**Dropped:**

- The contact page, the "más webs de viajes" page and the cookie pages.
- The country pages (`listing_location`). Almost every trip covers a single country, so these pages repeat the trip pages. The trip pages and trip cards still show the country.
- The 13 draft stages.
- The unused English test site (the `pya_en_*` tables).
- All plugins, comments, captcha and dynamic SEO.
- The stage rating (`_et_author_rating`).
- The image alignment classes (`alignleft`, `aligncenter`, `alignnone`). Every image becomes its own block, and the layout decides how images look.

### Static site generator: Astro

The site is built with [Astro](https://astro.build), for these reasons:

- **Flexibility for the redesign.** The visual design will be iterated after the first version. In Astro every piece of a page (header, stage card, map, gallery) is a component with its own markup and styles, so it is easy to change or replace.
- **Any JS or CSS library can be used**, and JavaScript only ships where it is asked for. The map is the only interactive part, and everything else is plain HTML.
- **Content collections validate the content** with a schema. For example, a stage without coordinates fails the build.
- **Built-in image optimization** and **built-in i18n routing.** Both are described below.
- **No new tooling for the owner,** who already uses Node and npm.

### Hosting: GitHub Pages

The repository already lives on GitHub as a public repository. A GitHub Actions workflow builds the site with `withastro/action` and publishes it with `actions/deploy-pages` on every push to `main`. The custom domain is configured with `public/CNAME`, and Pages provides HTTPS.

There is no preview on a `*.github.io` URL: the site is built for the root of its own domain, and a project page would live under a sub-path. Instead, the site is checked locally with `npm run build` and `npm run preview`, and then the DNS of `piedresyarena.com` is pointed to GitHub Pages:

- A and AAAA records for the apex domain;
- a CNAME record for `www`.

Any existing email records for the domain must be kept.

### Home page: map and trip cards

The home page keeps the essence of the current site:

- **A map at the top:**
  - built with Leaflet and OpenStreetMap tiles, so no API key is needed;
  - one marker per stage, placed with the coordinates from the dump and coloured by trip;
  - each marker has a popup that links to its stage.
- **One card per trip below the map,** from newest to oldest. Each card shows:
  - the featured image of the trip's first stage;
  - the trip name, country, year and number of stages;
  - the trip's map colour.

  The cards are in one column on mobile and two or three on desktop.
- **Each card links to the trip page,** which lists the trip's stages in order with their image and short description. Each stage page has previous and next links within its trip.

### New URL structure

The WordPress URLs are replaced by a simpler structure. The slugs are in Spanish, because they are part of the site content.

| Content | Old URL | New URL |
|---|---|---|
| Home | `/` | `/` |
| Trip | `/listing_type/<trip>/` | `/viajes/<trip>/` |
| Stage | `/listing/<stage>/` | `/viajes/<trip>/<stage>/` |
| About page | `/a-los-pedales/` | `/sobre-mi/` |
| Country | `/listing_location/<country>/` | dropped (redirected) |

The slugs are generated as follows:

- **Trip slugs** follow `<name>-<year>`, such as `georgia-2019` or `camino-primitivo-2016`. The year keeps them unique if a country is visited again.
- **Stage slugs** drop the trip prefix that WordPress needed, because the trip is already in the path. For example, `/listing/georgia-2-de-zhinvali-a-atabe/` becomes `/viajes/georgia-2019/2-de-zhinvali-a-atabe/`. Stages that were only numbered become `etapa-N` (for example, `mongolia-bike-challenge-2010-primera-etapa` becomes `etapa-1`), and the only stage of a single-stage trip is called `relato`.

The mapping from every old stage slug to its trip and new slug is an explicit, hand-reviewed table in `tools/migrate.py`, not a set of slug rules.

All URLs end with a trailing slash (`trailingSlash: 'always'`).

### Redirects from the old URLs

Every old public URL redirects to its new equivalent, so search engines and external links keep working:

- each `/listing/<stage>/` to its new stage URL, including the old slugs kept in `_wp_old_slug`;
- each `/listing_type/<trip>/` to its trip page;
- `/a-los-pedales/` to `/sobre-mi/`;
- each `/listing_location/<country>/` to the trip page when the country belongs to a single trip, and to the home page otherwise.

The migration script generates the mapping from the dump into `src/redirects.json`, which `astro.config.mjs` passes to Astro's `redirects` config. GitHub Pages has no server-side redirects, so Astro emits a small HTML page for each old URL. That page has a `<meta http-equiv="refresh">` redirect and a canonical link to the new URL.

Old image URLs (`/wp-content/uploads/…`) are not redirected.

### Images: colocated and optimized by Astro

Each image lives next to the content that uses it instead of in a global uploads folder. Every stage is a folder with its Markdown file and its images:

```
src/content/stages/es/georgia-2019/2-de-zhinvali-a-atabe/
├── index.md
├── atabe.jpg
└── …
```

Images are referenced with relative paths, both in the front matter (`image: ./atabe.jpg`) and in the body. Astro processes them at build time:

- it generates several widths of each image, and a `srcset` and `sizes` that match the width actually displayed (`image.layout: 'constrained'`);
- it converts them to modern formats such as WebP;
- it adds `width` and `height` to avoid layout shifts.

Only the original of each of the 318 referenced images is copied, never the WordPress thumbnails. While copying, the migration script applies the EXIF orientation, downscales the image to at most 1600 px on its long edge, and saves it without EXIF data, so no GPS or camera metadata ends up in the public repository. A stage can be moved or deleted as a single folder.

### Content conversion

A one-off script, `tools/migrate.py`, reads the SQL dump directly. It does not need a running database, and it can be re-run.

It writes one folder per stage with an `index.md` and its images. The metadata goes in the front matter, validated by the schema in `src/content.config.ts`:

- `title`, `date`, `trip` (a reference to `trips.yaml`)
- `lat`, `lng`, `address` (optional)
- `description`, `image`
- `seoTitle`, `seoDescription` (optional)
- `translationKey`

The post body keeps its inline HTML (links, emphasis) inside the Markdown file, so nothing is lost in a lossy HTML-to-Markdown conversion. Images are the exception: they become Markdown image syntax, because Astro only optimizes Markdown images, not raw `<img>` tags. The script makes these changes to the body:

- Every image becomes `![alt](./file.jpg)` in its own paragraph. A `[caption]` puts its text in the image title, `![alt](./file.jpg "Caption")`, and a small rehype plugin (`src/lib/rehype-figure.mjs`) turns that into `<figure>` with `<img>` and `<figcaption>`.
- `[button link=…]Siguiente etapa >[/button]` is removed. The stage layout already provides previous and next navigation.
- `[tabs]/[imagetab]` and `[easingslider]` become a simple image gallery.
- Bare YouTube URLs and iframes become responsive `<iframe>` embeds (`youtube-nocookie.com` for the bare URLs).
- Pasted inline styles are removed; a strike-through becomes `~~…~~`.
- Image URLs are rewritten to relative paths of the colocated files. No other internal links remain once the buttons are gone.

Single newlines inside a paragraph were line breaks in WordPress. `remark-breaks` keeps them as line breaks.

Astro 7 uses its own Markdown processor (Sätteri) by default, which does not run remark or rehype plugins. The site uses the remark/rehype processor instead, through `unified()` from `@astrojs/markdown-remark`, so these plugins work.

The script also generates the redirect mapping and reports any missing image, unconverted shortcode or unresolved internal link.

### Groundwork for a future English version

The site is Spanish-only for now. An English version is planned for some time in the future, so the structure is prepared for it now at almost no cost:

- **Routing.** Astro i18n is configured with `defaultLocale: 'es'`, `locales: ['es', 'en']` and `prefixDefaultLocale: false`. The Spanish URLs above stay unprefixed and never change. English pages will live under `/en/`, for example `/en/trips/georgia-2019/2-from-zhinvali-to-atabe/`.
- **Content by locale.** Content is stored per locale (`src/content/stages/es/…`, `src/content/pages/es/…`). Translated content will go in a sibling `en/` folder with its own, translated slugs.
- **Translation key.** Each stage and page has a `translationKey` in its front matter, shared by all of its translations. It links the language versions so a language switcher and `hreflang` tags can be built later.
- **No hardcoded interface text.** Labels such as "Siguiente etapa", "Viajes" and "Sobre mí", stage counters and date formats come from a per-locale dictionary (`src/i18n/es.ts`). Adding English means adding `en.ts`, not editing components.
- **Language attribute.** `<html lang>` is set from the current locale.

The English pages, the language switcher, the translated trip names and map popups, and the policy for untranslated content are left for when the translation happens.

### Repository language

Everything in the repository is written in English: code, comments, front matter keys, documentation and commit messages. The only exception is the website content, which is in Spanish.

## Alternatives considered

### Generator

- **Keep WordPress.** Rejected: it is the source of the problems this ADR solves.
- **Hugo.** It is a single binary with no dependencies, it is very stable, and it handles taxonomies and previous/next links out of the box. Rejected because Go templates are awkward to work with and limit the flexibility needed for the redesign.
- **Eleventy.** It is simple and stable, with readable templates. Rejected because trip grouping and stage navigation would have to be built by hand, and it has no component model.
- **Hand-written HTML.** Rejected: 65 pages share one layout, so every design change would have to be repeated 65 times.

### Hosting

- **Cloudflare Pages or Netlify.** Both offer preview deployments and server-side redirects. Rejected because they add another account, and GitHub Pages is enough for a public repository.
- **The current hosting over FTP.** Rejected because it keeps paying for PHP hosting that is no longer needed, and publishing would be a manual step.

### Home page

- **A list of trips only.** It is the simplest and lightest option. Rejected because it loses the map, which defines the current site.

### URLs

- **Keep the WordPress URLs.** Rejected for simplicity. `/listing/`, `/listing_type/` and the trip prefix repeated in every stage slug are WordPress theme artifacts. Redirects cover the old links.
- **Keep the images at `/wp-content/uploads/`.** Rejected: the images would be served unoptimized and kept apart from their content.

## Consequences

- **Editing:** a stage is edited by changing a Markdown file and pushing. A new stage is added by creating a folder with an `index.md` and its images. There is no admin panel, database or plugin to keep up to date.
- **Security and cost:** there is nothing to attack and nothing to pay for beyond the domain.
- **Maintenance:** Node dependencies need an occasional update (`npm update`, Astro upgrades).
- **Repository size:** the images live in the repository and add about 70 MB (318 images at up to 1600 px). That is acceptable for GitHub Pages. If it grows too much, the images can be moved to Git LFS or an external store.
- **Build time:** image optimization makes builds slower. That is acceptable for a site of this size.
- **Links and SEO:**
  - Old links keep working through HTML redirects. These are slightly weaker for SEO than HTTP 301 redirects, but search engines follow them and the canonical tags point to the new URLs.
  - Old direct image URLs stop working.
- **Content features:** content that relied on plugins is simplified. The slider becomes a static gallery, image alignment is left to the layout, and the cookie banner and SEO plugin disappear. The SEO titles and descriptions are kept as front matter.
- **Future translation:** adding English later is additive. It needs new content folders and a dictionary, with no change to the existing URLs.
- **Design:** the first version focuses on content parity. The visual design will be iterated later.

## Out of scope for the first version

- GPX tracks of the routes. The owner has GPX files for some trips and will decide later whether to publish them. If they are published, they would be drawn on the same map.
- Introductory texts for each trip. They could be added later as one Markdown file per trip.
- Interaction between the trip cards and the map, such as highlighting a trip's markers on hover.
- The English version itself. Only the groundwork described above is in scope.
